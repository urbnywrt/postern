# Postern: установка ноды одной командой Docker

- **Дата:** 2026-10-08.
- **Статус:** принят владельцем. Решено: образ лежит в реестре (ghcr.io), не в панели.
- **Дополняет:** `2026-10-04-postern-design.md`, §5.2 (установка ноды) и §7 (PKI).

## 1. Зачем

Сейчас ноду ставят так:
1. скачивают два архива: кит и бандл с закрытым ключом;
2. копируют их по `scp`;
3. запускают `install.sh` на 965 строк.

Владелец хочет одну команду `docker run`, как у других панелей. Старый путь остаётся запасным для сервера, который не видит панель.

## 2. Как это выглядит

Администратор добавляет ноду и нажимает «Получить команду». Панель показывает:

```sh
docker run -d --name postern-agent --restart unless-stopped \
  --network host --pid host --read-only --tmpfs /tmp \
  --log-opt max-size=10m --log-opt max-file=3 \
  -v /var/run/docker.sock:/var/run/docker.sock -v /opt/postern:/opt/postern \
  -v /etc/os-release:/host/etc/os-release:ro \
  -e POSTERN_JOIN='https://panel.example#<токен>' \
  ghcr.io/<OWNER>/postern-node:v1.0.0
```

Рядом показан тот же вариант в виде `compose.yaml`. Команда работает один раз и действует 24 часа. Через несколько секунд нода появляется в панели. Открыть порт управления для панели, как и раньше, надо самому, если не включён скрытый режим.

## 3. Решения

**3.1. Токен присоединения.**
- Это 32 случайных байта в base64url. Панель хранит только SHA-256 и срок, у ноды один действующий токен.
- `NodeService.CreateJoinToken` выпускает новый токен (только администратор). Предыдущий при этом сразу перестаёт действовать. В журнал пишется `node.join_token`.
- Значение `POSTERN_JOIN` имеет вид `<базовый URL панели>#<токен>`.
- Базовый URL нода принимает только по `https://`. По `http://` можно ходить лишь на loopback, для e2e. Ответ содержит CA, которому нода потом верит, поэтому подмена в пути недопустима.
- Нода ходит к панели без `HTTPS_PROXY`, как и при прочих загрузках (решение S5-16).

**3.2. Ключ остаётся на ноде.**
- Нода сама создаёт ключ ECDSA P-256 и отправляет CSR. Панель берёт из CSR только открытый ключ и проверяет подпись CSR.
- Сертификат панель выпускает с теми же полями, что `IssueServer`: CN — id ноды в нижнем регистре, SAN `<id>.internal`, serverAuth, 10 лет.
- Панель сохраняет `cert_pem` и `cert_fingerprint`, а `key_enc` обнуляет. После присоединения закрытого ключа в панели нет, и бандл для такой ноды не скачивается (409).
- `CreateNode` по-прежнему сразу выпускает ключ и сертификат, чтобы путь кита работал без изменений. Присоединение их заменяет: побеждает последний способ.

**3.3. `JoinService.Join`.**
- Это публичная процедура Connect, без сессии, тело до 64 КиБ.
- Запрос: токен, CSR (DER), архитектура и версия ноды.
- Ответ: `node_id`, `mgmt_port`, `ca_pem`, `cert_pem`.
- **Неудачи ограничены по адресу клиента** тем же ограничителем, что у входа: 5 за 15 минут, затем блокировка.
- **Повтор того же CSR тем же токеном** в течение срока токена возвращает тот же сертификат. Так переживается ответ, потерянный в сети: нода хранит свой ключ до успешного присоединения.
- **Журнал:** `node.join` с адресом клиента в `details.source`.
- **Адрес управления может быть пустым** при создании ноды. Тогда присоединение подставляет адрес клиента, если он публичный одноадресный: не частный, не loopback, не CGNAT. Иначе нода ждёт, пока администратор впишет адрес.
- **Менеджер соединений не трогает ноду без адреса управления.** Она остаётся `provisioning`, а не `error`.
- После присоединения панель сразу подключается к ноде с новым отпечатком.

**3.4. `postern-node bootstrap`: точка входа образа.** Он выполняется до launcher-а и агента, по шагам:
1. **Проверка окружения.** Корень, Docker отвечает, user namespaces не переназначены (новый `dockerapi.Client.Info`). Своего контейнера bootstrap ищет через Docker. Если нашёл, проверяет, что `POSTERN_HOME` смонтирован с тем же путём на хосте; иначе отказывается и объясняет почему. Не нашёл — только предупреждение.
2. **Раскладка `/opt/postern`.** Каталоги и права те же, что у `install.sh`.
3. **Присоединение.** Нужно, если ключей нет или в `POSTERN_JOIN` новый токен: его SHA-256 не совпадает с записанным в `data/state/join-token.sha256`.
   - Ключи пишутся атомарно в том же виде, что из бандла (`pki/{ca.pem,node.pem,node-key.pem,bundle.json}`), поэтому агент не меняется.
   - Состояние чужой ноды откладывается в сторону, как это делает `install.sh`.
   - Если присоединение не удалось, а рабочие ключи есть, bootstrap предупреждает и запускает ноду со старыми ключами. Если ключей нет, он выходит с кодом 1, и Docker перезапускает контейнер.
4. **Бинарник.**
   - Бинарник образа копируется в `bin/postern-node-<версия>`, а если в образе есть подпись — и в `bin/.postern-node-<версия>.minisig`. Вместе с ним кладётся `bin/launcher.sh`.
   - `bin/current` переключается на него, если `current` нет или версия образа новее. Прежний `current` становится `previous`.
   - Более старый образ ничего не понижает: самообновление уже ушло вперёд.
   - Версия с тем же именем, но другим содержимым не заменяется: bootstrap предупреждает и оставляет текущую.
5. **Настройки ядра.** Одноразовый привилегированный контейнер на образе-раннере, в сети хоста, делает то же, что шаг 7 `install.sh`:
   - резервирует порты 20000–40999, объединяя с уже зарезервированными;
   - включает `tcp_migrate_req=1`;
   - пишет файл `/etc/sysctl.d/90-postern.conf`.

   Шаг повторяется при каждом старте, поэтому переживает перезагрузку. Неудача — предупреждение, не ошибка. Агент и так держит сокет Docker, так что привилегированный помощник не даёт ему новых прав.
6. **Запуск агента:** `exec /opt/postern/bin/launcher.sh agent`. Агент работает из `bin/current` на хосте, как сейчас: edge монтирует его по пути хоста.

`ENTRYPOINT ["/usr/local/lib/postern/postern-node"]`, `CMD ["bootstrap"]`: `docker run --rm <образ> version` работает. Метки `postern.managed/role/id` заданы в образе.

**3.5. Образ и релиз.**
- Образ собирается по `deploy/node/Dockerfile`: тот же раннер alpine по дайджесту, бинарник из исходников или из `PREBUILT`, для amd64 и arm64.
- В `release.yml` его собирает задача `image`, если задана переменная репозитория `POSTERN_NODE_IMAGE`. Теги те же, что у образа панели.
- Ссылку на образ панель берёт из `POSTERN_NODE_IMAGE`:
  - значение по умолчанию вшивается при сборке (ldflag `version.NodeImage`), переменная окружения его переопределяет;
  - если в ссылке нет тега и дайджеста, добавляется `:<версия панели>`;
  - у сборки `dev` без тега команды нет, страница ноды объясняет почему.
- `GetNodeInstall` отдаёт `node_image`.

**3.6. Интерфейс.**
- **Основной блок установки** на странице ноды и в окне «Нода создана» — «Установка одной командой». В нём:
  - кнопка выпуска токена;
  - вкладки `docker run` и `compose.yaml`;
  - напоминание о файрволе.
- **Поле «Адрес панели для нод»** заполняется из `location.origin`, его можно править, и браузер его запоминает. Без `https://` оно отказывает, кроме loopback.
- **Кит и бандл** убраны в раскрывающийся блок «Без Docker-реестра».
- **Адрес управления при создании ноды** необязателен.
- **Подсказки, где сказано «запустите install.sh снова»**, говорят и о ноде в Docker: достаточно `docker restart postern-agent`.

**3.7. Установка по SSH.** Если образ известен и мастер передал адрес панели, задача установки:
1. выпускает токен;
2. проверяет сервер (Compose, bash 4 и кит больше не обязательны);
3. при необходимости ставит Docker;
4. удаляет старый контейнер `postern-agent`, если он есть;
5. выполняет ту же команду `docker run` и ждёт, пока нода выйдет на связь.

Иначе установка идёт старым путём кита.

## 4. Не делаем сейчас

- Раздачу образа самой панелью.
- Закрепление образа по дайджесту в подписанном манифесте релиза.
- Обратное соединение «нода → панель».
- Автоматическое правило файрвола.
- Смену стиля установки у нод, поставленных китом. Они работают как есть. Чтобы перейти на Docker, достаточно `docker compose -f /opt/postern/compose.yaml down` и команды из панели с новым токеном.
