# Postern — дизайн v1

- **Дата:** 2026-10-04
- **Статус:** принят (дизайн согласован по секциям; реализация идёт срезами, см. §12)
- **Лицензия проекта:** AGPL-3.0

Postern — панель и нода для развёртывания, управления и мониторинга MTProto-прокси
(fake TLS и Telegram WEB) на парке серверов. Проект пишется с нуля.

---

## 0. Цели, не-цели, принятые решения

### 0.1 Цели v1

1. Панель: разворачивание нод (по SSH), администрирование и контроль в одном месте,
   генерация ссылок и QR, сбор статистики.
2. Универсальная нода: несколько реализаций MTProxy (telemt, mtg) с переключением
   на лету без смены ссылки; умная диагностика; фоллбек выхода и фоллбек для чужих.
3. Обновления без пересборок: версия движка видна у каждого прокси и меняется
   кнопкой, без простоя; самообновление ноды и панели.
4. WEB-прокси: свой 443, второй IP или совместно с чужим сайтом по `base_path`
   (свой 443 не обязателен).
5. Выходы: VLESS/VMess/Trojan/SS (URI и подписки), WARP, Psiphon, socks/http,
   прямой выход с выбором интерфейса; цепочки с фоллбеком.
6. Публичная страница со ссылками на отдельном домене.
7. Проект публичный с первого коммита: никаких реальных адресов и секретов в истории.

### 0.2 Не-цели v1 (в бэклоге)

Сущность «клиент» (прокси = ссылка), продажа/оплата, Telegram-бот, бэкапы по
расписанию, проверка доменов пула, перекрёстные пробы между нодами, общий
экземпляр telemt на много прокси, маршрутизация по секрету (несколько прокси на
одном SNI), типы dd/classic без TLS, Prometheus, роли админов, API-токены, IPv6 на
входе, автоматический откат движка при деградации (только отмена неудачного обновления),
ACME TLS-ALPN-01, отдельный UID на экземпляр движка с nft-ограничением исходящих
на loopback, бюджет FD/памяти в диагностике.

### 0.3 Решения, принятые с владельцем проекта

| Вопрос | Решение |
|---|---|
| Модель | прокси = ссылка (как сейчас), лимит устройств на ссылку |
| Фоллбек | выхода (цепочки) и для чужих (маска/отказ); не входа (DNS) и не движка |
| Связь | панель звонит в ноду; gRPC поверх mTLS |
| Архитектура | Go-агент + edge, движки и выходы — контейнеры Docker |
| Публичная страница | на отдельном домене, открыта на корне домена, `noindex` по умолчанию |
| Имя / лицензия | Postern / AGPL-3.0 |
| Репозиторий | приватный Gitea сейчас, публичный GitHub позже |
| Коммиты | автор — псевдоним владельца с noreply-адресом, без трейлеров соавторства |

## 1. Глоссарий

- **Панель** — веб-приложение администратора (Go + SQLite + встроенный React).
- **Нода** — сервер с установленными контейнерами Postern.
- **Агент** (`postern-node agent`) — управляющий процесс ноды: состояние, Docker,
  обновления, диагностика, API для панели.
- **Edge** (`postern-node edge`) — трафиковый процесс ноды: принимает клиентов на
  портах прокси, маршрутизирует по SNI, терминирует WEB, держит лимиты и счётчики,
  а также маршрутизирует исходящий трафик движков по цепочкам выходов.
- **Вход** (listener) — пара `IP:порт` на ноде, которую слушает edge.
- **Прокси** — одна ссылка: вход + тип + секрет + домен + движок + выход + лимиты.
- **Движок** — реализация MTProxy (telemt, mtg); **экземпляр движка** — контейнер.
- **Выход** (egress) — способ дойти до Telegram: direct, socks/http, Xray, warp-plus.
- **Цепочка** — упорядоченный список звеньев выхода с проверками и фоллбеком.
- **Поколение** (generation) — монотонный номер версии: желаемого состояния ноды,
  экземпляра движка, экземпляра edge.

## 2. Архитектура

```
Панель — 1 Docker-контейнер: Go + SQLite + встроенный React
   │  gRPC поверх mTLS (панель → нода); SSH только при разворачивании
   ▼
┌──────────── Нода: Docker, все контейнеры в host network ─────────────┐
│ postern-agent          управление        postern-edge-g<N>  трафик   │
│  · желаемое состояние   · Docker API      · вход: SNI → движок        │
│  · обновления, ACME     · диагностика     · чужие → маска/отказ       │
│  · статистика → панели                    · WEB: TLS + HTTP/2         │
│                                           · выход: SOCKS → цепочки    │
│ postern-eng-<id>-g<N>  telemt / mtg       postern-egr-<id>-g<N>       │
│   127.0.0.1:порт, PROXY v2                xray / warp-plus (SOCKS)    │
└───────────────────────────────────────────────────────────────────────┘
клиент → edge ─SNI→ движок ─SOCKS→ edge (цепочка) → VLESS/WARP/Psiphon/direct → DC
```

**Принципы**

1. **Декларативность.** Панель хранит желаемое состояние и отправляет ноде его
   целиком с номером поколения. Нода приводит себя к нему (reconcile) и сообщает
   применённое поколение и фактическое состояние. Императивных «создай/пауза» нет.
2. **Автономность ноды.** Нода хранит последнее состояние локально и работает без
   панели; статистика копится и догружается позже.
3. **Никаких IP контейнеров.** Все контейнеры в `network_mode: host`, внутренние
   сервисы слушают только `127.0.0.1` на портах, выделенных агентом.
4. **Никаких своих образов на ноде.** Все контейнеры ноды запускаются из
   стандартного `alpine` (закреплён по digest) с примонтированными бинарниками,
   проверенными по sha256 (сторонние) или подписи (наши). Версия = какой бинарник
   смонтирован.
5. **Трафик не зависит от управления.** Обновление и падение агента не трогают
   edge, движки и выходы. Edge обновляется отдельно с передачей портов
   (`SO_REUSEPORT`), без простоя.
6. **Безопасные изменения.** Любая смена, требующая перезапуска процесса, идёт
   через blue-green: новое поколение рядом → проверки → переключение → слив
   старого. Провал проверок = отмена, старое поколение продолжает работать.

**Правила**

- Вход владеет портом: конфликт (порт занят remnawave/nginx/чем-то ещё) виден в
  модели и в диагностике, а не всплывает ошибкой при запуске.
- На входе `tls` по SNI может жить сколько угодно прокси (fake TLS и WEB вперемешку),
  домены уникальны в пределах входа.
- Входы одной ноды не перекрываются: на одном порту — либо `0.0.0.0`, либо
  конкретные адреса (не одновременно). Нарушение отклоняется при валидации
  состояния; занятость порта чужим процессом ловит предпроверка.
- Вход `http-upstream` — внутренний `127.0.0.1:порт` для WEB, который сидит за
  чужим веб-сервером (режим `base_path`, §5.4).
- **Лимиты.** `limit_devices` — уникальные IP (основной «лимит устройств»; в UI
  подписывается «уникальные IP», т.к. за CGNAT много устройств на одном IP);
  `limit_conns_total` — одновременные соединения прокси; `limit_conns_per_ip` —
  соединения с одного IP. `0` = без лимита.
- Хранение статистики по умолчанию: 1m — 48 ч, 1h — 90 дней, 1d — бессрочно.
  `ip_sightings` — 7 дней; политика IP: `full` | `countries` | `off` (§8.6).

## 4. Ссылки (контракт, байт в байт)

`enc(x)` — точная семантика JavaScript `encodeURIComponent`: не экранируются
`A-Z a-z 0-9 - _ . ! ~ * ' ( )`, остальное — `%XX` в верхнем регистре по байтам UTF-8.
`hex(x)` — шестнадцатеричная запись байтов UTF-8 строки, **строчными**.
Секрет и домен хранятся **как есть** (без нормализации регистра) — иначе
выданные ссылки изменятся.

**Fake TLS**

```text
host   = listener.link_host_override || node.link_host
secret = "ee" + secret32hex + hex(domain)
tg://proxy?server={enc(host)}&port={listener.port}&secret={secret}
https://t.me/proxy?server={enc(host)}&port={listener.port}&secret={secret}
```

**WEB, корень (`base_path` пуст)** — хост из домена прокси, порта нет:

```text
s = plain ? secret32hex : "dd" + secret32hex
https://t.me/webproxy?server={enc(domain)}&secret={s}
tg://webproxy?server={enc(domain)}&secret={s}
```

**WEB с путём** (telemt ≥ 3.5.8): `server = enc(domain + "/" + base_path)`,
`secret = base64url_nopad(0x70 || client_secret)`, где `client_secret` — 16 сырых
байт секрета (`plain`) или `0xdd || 16 байт` (`dd`).

**Эталонные формулы** (зафиксированы золотыми векторами
`internal/links/testdata/reference_vectors.json`, генератор `gen_vectors.mjs`):
`tg://proxy` — `server=encodeURIComponent(host)`, `port = listener.port`,
`secret = 'ee' + secret + Buffer.from(domain,'utf-8').toString('hex')`;
WEB — `https://t.me/webproxy?server=encodeURIComponent(domain)&secret=(dd?)secret`.

## 5. Нода

### 5.1 Раскладка на хосте

```text
/opt/postern/
  compose.yaml                 # только сервис postern-agent
  bin/  launcher.sh  postern-node-<ver>  current -> postern-node-<ver>  previous -> ...
  pki/  ca.pem  node.pem  node-key.pem   (0600)
  data/
    state/desired.json  desired.prev.json  runtime.json   # атомарная запись
    edge/config-g<N>.json                                  # последняя таблица edge
    run/edge-g<N>.sock  launcher/                           # сокеты и маркеры
    artifacts/<engine>/<version>/<arch>/<binary>            # проверенные бинарники
    instances/<instance-id>/  (config, data, public/)       # файлы экземпляров
    certs/<domain>/  fullchain.pem  privkey.pem  meta.json
    acme/  account.json
    stats.db                                                # буфер статистики, 7 дней
```

**Контейнеры** (все `network_mode: host`, метки `postern.role`, `postern.id`,
`postern.generation`, `postern.managed=true`):

| Контейнер | Кто создаёт | Пользователь, права | Монтирование |
|---|---|---|---|
| `postern-agent` | compose | root, `read_only`, `pid: host` (только чтение — опознать владельцев портов) | docker.sock, `/opt/postern` |
| `postern-edge-g<N>` | агент | root, `cap_drop: ALL`, `cap_add: NET_BIND_SERVICE` (+`NET_RAW` при выходе через интерфейс), `read_only` | `bin` (ro), `data/edge`, `data/run`, `data/certs` (ro) |
| `postern-eng-<id>-g<N>` | агент | `65534:65534`, `cap_drop: ALL`, `no-new-privileges`, `read_only`, tmpfs `/tmp`, лимиты памяти/pids | бинарник (ro), каталог экземпляра |
| `postern-egr-<id>-g<N>` | агент | как у движков | бинарник (ro), каталог экземпляра |

Политика перезапуска у активных поколений — `unless-stopped`; у сливаемых — `no`.
После перезагрузки сервера Docker сам поднимает edge (с последней таблицей),
движки и выходы — даже если агент не стартовал.

**Порты на `127.0.0.1`** (агент выделяет, проверяет занятость, хранит в `runtime.json`):
движки 20000–24999, API/метрики движков 25000–29999, SOCKS edge для движков
30000–34999, SOCKS выходов 35000–39999, служебные (тестовый вход, mgmt, http-upstream)
40000–40999. Порт управления (mTLS) — на внешнем интерфейсе, выбирается при
разворачивании (случайный высокий), меняется в панели.

### 5.2 Агент

Обязанности: gRPC-сервер для панели (§6); хранение желаемого состояния
(запись: tmp → fsync → rename → fsync каталога; предыдущее поколение
сохраняется); цикл согласования; хранилище артефактов; драйверы движков и выходов;
ACME; диагностика; сбор статистики; потоки логов; самообновление.

**Цикл согласования** (по событию «новое состояние» и раз в 30 с):

1. Прочитать желаемое состояние, `runtime.json` и фактическое (контейнеры по
   меткам, файлы, состояние edge).
2. Построить план: выходы → артефакты → экземпляры движков (новые поколения) →
   таблица edge → слив старых поколений → уборка.
3. Выполнить шаги идемпотентно; каждый шаг — событие в журнал ноды.
4. Сообщить панели `applied_generation`, состояние каждого прокси
   (`pending|starting|ready|serving|draining|failed` + причина) и события.

После рестарта агент **находит свои контейнеры по меткам** и продолжает, а не
создаёт дубли. Чужие контейнеры агент не трогает никогда.

**Сериализация.** Согласование выполняет один рабочий поток. Новое состояние,
пришедшее во время прохода, не применяется параллельно: текущий шаг доводится
до безопасной точки, проход прерывается и начинается заново с самым новым
поколением. Поколение меньше уже принятого отклоняется. При старте агент
приводит к норме инварианты: ровно одно активное поколение edge (лишние —
слив), ровно одно обслуживающее поколение на прокси.

### 5.3 Edge: вход

- **Приём.** На каждый вход `tls` — сокет с `SO_REUSEPORT`. Чёрный список (CIDR)
  проверяется сразу после `accept`. Затем чтение ClientHello с таймаутом 10 с,
  сборка из нескольких TLS-записей (до 64 КиБ), разбор SNI и ALPN. Парсер покрыт
  фаззингом.
- **Маршрутизация** по `(вход, SNI)`; таблица меняется атомарно (подмена указателя).
  - fake TLS → `127.0.0.1:<порт движка>`: заголовок PROXY v2 (реальный IP клиента),
    затем буферизованный ClientHello, затем двусторонняя пересылка.
  - WEB → терминация TLS в edge (§5.4).
  - SNI управления (режим `hidden`) → сырой TCP с PROXY v2 на **скрытый** слушатель
    агента `127.0.0.1:<порт>`. Этот слушатель **обязательно** сначала разбирает
    PROXY v2 (без него соединение закрывается), затем начинает mTLS. Обычный
    слушатель управления PROXY не принимает. Закрепляется тестом: панель через
    публичный порт с `mgmt_sni` проходит `GetInfo`.
  - **Чужие.** Неизвестный SNI → `stranger_action` входа:
    `mask` — сырой TCP на `mask_target` (по умолчанию: сам SNI, если он из пула
    доменов или домен одного из прокси; иначе `reject`); `reject` — TLS alert
    `unrecognized_name` (как `ssl_reject_handshake` у nginx); `drop` — закрыть после
    случайной задержки. Не-TLS трафик → `non_tls_action` (`drop` | ответ как у
    nginx «400 plain HTTP to HTTPS port»).
  - Известный SNI с неверным секретом (активная проба) маскирует сам движок.
- **Пауза** = маршрут снят, SNI обрабатывается как чужой; движок остаётся
  запущенным для быстрого возобновления.
- **Лимиты** (не зависят от движка): устройство = IP, у которого есть открытое
  соединение или было в последние 120 с; новое соединение с нового IP сверх
  `limit_devices` → поведение чужого. `limit_conns_total`, `limit_conns_per_ip` —
  семафоры. Для WEB действуют устройства и соединения на уровне TCP.
- **Счётчики** по прокси: байты вверх/вниз, соединения (активные, новые),
  активные устройства; по IP: активные соединения, последний раз, байты. Агент
  забирает снимки раз в 10 с. Перезапуск движка их не сбрасывает.
- **Таймауты пересылки:** простой 15 мин, полузакрытие поддерживается.

### 5.4 Edge: WEB

- **Терминация:** `crypto/tls` (TLS 1.2+, ALPN `h2`, `http/1.1`), HTTP/2 сервер,
  обратный прокси на WEB-слушатель telemt `127.0.0.1:<порт>`:
  `Host` сохраняется; `X-Forwarded-For` перезаписывается **одним** IP клиента;
  без буферизации (`FlushInterval: -1`); WebSocket Upgrade проходит; таймауты ≥ 65 с,
  лимит тела ≥ `web.limits.max_body_bytes` (2 МиБ); access-лог выключен (в запросах
  bearer-данные). telemt: `web_trusted_proxy_cidrs = ["127.0.0.1/32"]`.
- **Режимы:**
  1. **общий 443** — тот же вход `tls`, что и у fake TLS: WEB-SNI терминируются,
     fake TLS идёт сырым TCP. Реальный IP доходит до telemt.
  2. **отдельный IP:443** — вход `tls` на втором адресе.
  3. **совместно с чужим сайтом** — вход `http-upstream` на `127.0.0.1:<порт>`,
     `base_path` обязателен. Edge доверяет `X-Forwarded-For` только от
     `trusted_cidrs` входа (по умолчанию `127.0.0.1/32`; если чужой сервер в
     Docker bridge — добавляется его подсеть). Нода выдаёт сниппеты:
     Caddy — `handle /<base>/* { reverse_proxy 127.0.0.1:<порт> { header_up
     X-Forwarded-For {remote_host} } }` (**не** `handle_path`, он срезает префикс);
     nginx — `location ^~ /<base>/ { proxy_pass http://127.0.0.1:<порт>; ... }`
     без URI и rewrite **плюс** `location = /<base> { proxy_pass ...; }`, чтобы
     путь без слеша не превращался в 301 (вне контракта telemt). e2e проверяет
     запрос без слеша. Сертификатом владеет чужой сервер.
- **Сертификаты** (ACME, библиотека lego, в агенте). В v1 — только DNS-01 и
  импорт; TLS-ALPN-01 вынесен в бэклог (конфликт за `:443` с edge, нужен маршрут
  челленджа до выпуска и выбор сертификата по ALPN — сложность не окупается, пока
  есть DNS-01).
  - DNS-01 — Cloudflare (и другие провайдеры lego); учётные данные из
    `dns_credentials`. Проверка распространения TXT — **только через DoH**
    (UDP/53 бывает закрыт), уборка брошенных `_acme-challenge` перед выпуском,
    блокировка на домен, таймауты на все HTTP-клиенты.
  - `imported` — сертификат, загруженный администратором; нода его не выпускает.
  - Продление за 30 дней. Статус и ошибка последнего выпуска — в состоянии прокси.
  - Edge подхватывает новые сертификаты без перезапуска: `SetConfig` несёт
    поколение сертификатов, `GetCertificate` читает актуальную пару.
- **`public_addr`** в `[[web.vhosts]]` — всегда публичный IP, на который
  указывает A-запись домена, и порт 443 (он входит в кортеж внутреннего relay
  telemt). Берётся из DoH-резолва при применении и сверяется с публичными IP
  ноды; адрес привязки входа (`0.0.0.0`, `127.0.0.1`) сюда **никогда** не
  попадает. Не сошлось — состояние отклоняется с причиной.
- **Carrier по умолчанию:** `carrier = "https"` (его используют клиенты без
  согласования, в том числе Telegram iOS) и `carriers = ["https-lanes"]` для
  согласования с Desktop. Ссылку carrier не затрагивает, а iOS перестаёт
  отваливаться.
- **Предпроверки WEB** (до применения): A-запись (через DoH) совпадает с IP входа;
  запись не проксирована Cloudflare (адрес не из диапазонов CF); домен уникален;
  для режима 3 — `base_path` валиден по правилам telemt.
- **Сайт-приманка** генерируется детерминированно от id прокси (разные структуры,
  страницы, стили; только внешний CSS, без inline-скриптов и сторонних ресурсов),
  кладётся в каталог экземпляра; telemt `decoy.mode = "static_directory"`.

### 5.5 Движки

**Драйвер** (интерфейс в агенте): возможности (типы прокси, PROXY protocol,
hot-reload), рендер конфига, спецификация контейнера, проверка готовности,
статистика (опционально), шаблоны имён артефактов по архитектурам.

| | telemt | mtg v2 |
|---|---|---|
| Типы | fake TLS, WEB | fake TLS |
| Артефакт | `telemt-<arch>-linux-musl.tar.gz` (тег без `v`) | релиз GitHub `9seconds/mtg` (шаблон имени сверить) |
| Готовность | `GET /v1/health/ready` (API на `127.0.0.1`, заголовок авторизации) | порт принимает + метрики |
| Вход | `[[server.listeners]] ip="127.0.0.1" port=P proxy_protocol=true`; `[server] proxy_protocol_trusted_cidrs=["127.0.0.1/32"]` | `bind-to=127.0.0.1:P`, PROXY protocol на слушателе |
| Выход | `[[upstreams]] type="socks5" address="127.0.0.1:S"` дважды: без `scopes` и с `scopes="me, fetch"`; `[censorship] tls_fetch_scope="fetch"` | socks5-апстрим на `127.0.0.1:S` |
| Секрет | `[access.users]` — 32 hex | полный `ee` + секрет + hex(домен) |
| Промо-тег | есть (hot-reload) | **нет** (в mtg v2 ad tag убран) → переключение на mtg запрещено, пока у прокси задан `ad_tag` |

**Инварианты telemt-конфига**: весь трафик (включая `me`, `fetch`, TLS-front)
только через SOCKS edge — `direct` апстрима нет никогда; fake TLS:
`[general.modes] tls=true, classic=false, secure=false`, `[censorship] tls_domain`,
`mask=true`, `mask_host` (переопределение прокси или домен), `tls_emulation=true`;
`[access.users]` — один пользователь с секретом прокси; API — `127.0.0.1`,
`whitelist=["127.0.0.1/32"]`, случайный `auth_header`. WEB — как в §5.4 плюс
`[web]`, `[[web.vhosts]]` (`host`, `base_path`, `public_addr = <IP входа>:443`,
`decoy`, `profiles`), `[web.limits]`. Ручные переопределения (`engine_overrides`)
проверяются по схеме и не могут нарушить инварианты.

**Middle-proxy (ME).** Для новых прокси ME включается, только если задан промо-тег
(иначе прямой режим к DC). При включённом ME агент
пишет `middle_proxy_nat_ip = <внешний IP активного звена выхода>` и
`middle_proxy_nat_probe = false` (STUN — это UDP, через SOCKS не ходит). Смена
внешнего IP звена → пересоздание экземпляра по blue-green. До пересоздания ME
может быть неработоспособен; `me2dc_fallback = true` переводит новые сессии в
прямой режим к DC, поэтому прокси продолжает работать (без промо-тега) и после
пересоздания возвращается к ME. Если у прокси задан `nat_ip`,
`middle_proxy_nat_ip` берётся из него, а не из IP выхода.
(Проверить на стенде, §14.)

**Экземпляры.** В v1 — один экземпляр на прокси (`postern-eng-<proxy>-g<N>`).
Порты (вход, API, SOCKS edge) выделяются на поколение, поэтому два поколения
работают одновременно.

**Blue-green** — единая механика для смены движка, версии, параметров без
hot-reload и внешнего IP выхода:

1. Поднять поколение N+1 (новые порты).
2. Готовность (таймаут 90 с): health движка; проба L1 через тестовый вход edge
   (§5.7); CONNECT к DC через SOCKS-порт **этого** экземпляра по его цепочке;
   при включённом ME — ещё HTTPS до `core.telegram.org` тем же путём. Если DC
   доступны — проба L2. Одна L1 недостаточна: она не проходит выход.
3. Успех → edge атомарно переключает маршрут на N+1; N переходит в `draining`
   (новых соединений нет, текущие живут) и гасится, когда соединений 0 или через
   30 мин.
4. Провал → N+1 удаляется, прокси остаётся на N, событие `upgrade_aborted`.

Лимиты, пауза и чёрный список живут в edge и применяются мгновенно, движок не
трогается. Параметры движка с hot-reload (например, промо-тег у telemt) применяются
через его API без пересоздания; остальные — через blue-green.

Конфиг telemt задаёт слушатель только через `[[server.listeners]]` на `127.0.0.1`;
что telemt не открывает дополнительно `[server] port` по умолчанию, закрепляется
интеграционным тестом (слушающие сокеты экземпляра сверяются с ожидаемыми).

### 5.6 Выходы

**Поставщики**

| Вид | Где реализован | Детали |
|---|---|---|
| `direct` | edge | опционально `SO_BINDTODEVICE` (интерфейс, поднятый вне Postern: `wg0`, `tun0`…) или исходный IP |
| `socks5`, `http` | edge | внешний прокси с авторизацией |
| `xray-uri`, `xray-subscription` | `postern-egr-*` (Xray) | на каждый сервер — свой SOCKS-inbound `127.0.0.1:P` и свой outbound (1:1). Поддержка URI: `vless` (tcp/ws/grpc/xhttp/httpupgrade; tls/reality; flow), `vmess`, `trojan`, `ss`. Подписка: base64- или текстовый список URI; обновление раз в 6 ч и по кнопке; скачивание напрямую, при сбое — через живые звенья |
| `warp`, `psiphon` | `postern-egr-*` (warp-plus) | SOCKS на `127.0.0.1:P`; режимы WARP / WARP-in-WARP / Psiphon со страной; состояние регистрации WARP — в каталоге экземпляра |

**Звенья.** Подписка разворачивается в звенья по серверам, поэтому фоллбек между
серверами подписки и между разными видами выходов устроен одинаково и живёт в
одном месте — в edge.

**Маршрутизация в edge.** На каждый экземпляр движка — отдельный SOCKS5
`127.0.0.1:S` (прокси опознаётся по порту). telemt передаёт назначение запроса в
SOCKS-логине (`me`, `fetch`; пустой — обычный трафик к DC). Выход прокси —
цепочка по умолчанию плюс **необязательные переопределения по назначению**
(`egress_scope_chains`, например `{"me": <цепочка direct>}`: ME напрямую,
остальное через выход). CONNECT → выбранная цепочка: первое звено,
не помеченное упавшим; таймаут соединения 4 с → следующее звено; все упали →
отказ SOCKS. Текущие соединения при смене пути не рвутся; «сбросить соединения»
— отдельное действие.

SOCKS-порты экземпляров — стабильные имена в таблице edge: новое поколение edge
занимает **те же** порты (тоже с `SO_REUSEPORT`), поэтому движки при передаче
edge не теряют выход. Падение edge — это простой и входа, и выхода всех прокси
ноды; Docker поднимает его за секунды, это
описано в эксплуатационной документации.

**Проверки звеньев** (в edge, параметры от агента): раз в 30 с — TCP до DC1–5
(`149.154.175.50`, `149.154.167.51`, `149.154.175.100`, `149.154.167.91`,
`91.108.56.130`, порт 443), HTTPS до `core.telegram.org` (нужен ME), внешний IP
выхода (несколько эхо-сервисов по очереди). Гистерезис: упало после 3 неудач
подряд, живо после 2 успехов. Переключения → события и журнал. Звено признаётся
упавшим только по DC; недоступность эхо-сервисов или `core.telegram.org` даёт
предупреждение, но не роняет звено. Список адресов DC — настройка с разумным
значением по умолчанию, а не константа в коде.

### 5.7 Диагностика

Цель — найти первое место разрыва по цепочке клиент → edge → движок → выход →
Telegram. Результат проверки: `{id, layer, status: ok|warn|fail|skip, summary,
evidence, hint, fix?}`.

| Слой | Проверки |
|---|---|
| host | Docker; расхождение часов (по `Date` нескольких HTTPS-источников; warn > 2 с, fail > 30 с — fake TLS чувствителен); DNS (системный резолвер vs DoH, детект закрытого UDP/53); диск; публичные IP; владельцы портов входов |
| ingress | вход слушается; доступность снаружи — проба из панели |
| engine | контейнер, готовность, состояние DC и ME (`/v1/stats/dcs`), известные ошибки в логах («All ME servers for DC failed», «proxy-secret is unavailable», …) → причина |
| egress | по каждому звену: DC, HTTPS, внешний IP, задержка, история |
| web | A-запись (DoH), «оранжевое облако», сертификат и срок, HTTP/2, приманка, `base_path` |
| e2e | синтетическая проба (ниже) |

**Синтетическая проба** — MTProto-клиент с секретом прокси:
- **L1 (без интернета):** fake-TLS ClientHello с HMAC → проверка ServerHello от
  движка (доказывает маршрут edge и секрет). Используется как гейт blue-green.
- **L2:** L1 + obfuscated2 + `req_pq_multi` → `resPQ` от DC — вся цепочка
  «глазами клиента». Запускается с ноды (через тестовый вход) и из панели (снаружи).

Лёгкие проверки идут постоянно, полный прогон — по кнопке и **автоматически до и
после** обновлений и смены выхода. Безопасные
исправления в один клик: пересоздать экземпляр, сменить выход, перевыпустить
сертификат, перезапустить edge.

### 5.8 Статистика на ноде

Агент раз в 10 с снимает счётчики edge, метрики хоста (CPU, память, load, диск,
сеть) и здоровье звеньев; пишет минутные агрегаты в `stats.db` (хранение 7 дней);
каждая запись получает монотонный номер. Панель читает поток `Watch` с курсора и
после простоя догружает пропущенное. IP-наблюдения отправляются только если
политика IP это разрешает.

## 6. Протокол панель ↔ нода

**Транспорт.** gRPC (connect-go, протокол gRPC) поверх mTLS. Контракт — protobuf
в `proto/postern/node/v1`, совместимость проверяется `buf breaking`. Панель
поддерживает ноды предыдущей минорной версии (поэтапная раскатка).

**PKI.** При первом запуске панель создаёт CA (ECDSA P-256), ключ хранится
зашифрованным. Ноде выпускается серверный сертификат (`node.pem`), панели —
клиентский. Нода принимает только клиента, подписанного CA; панель проверяет
цепочку и **запоминает отпечаток** сертификата ноды. SNI при подключении —
`mgmt_sni` ноды: в режиме `hidden` это правдоподобный домен (не из доменов
прокси), который edge пересылает агенту; сканер видит обычный TLS-сервер с маской.

**Вызовы `NodeService`**

| Вызов | Назначение |
|---|---|
| `GetInfo` | версии агента/edge/движков, архитектура, ОС, публичные IP, возможности, владельцы портов |
| `ApplyState(state, generation)` | принять желаемое состояние; ответ — принято/отклонено с причиной валидации |
| `Watch(cursor)` | серверный поток: состояние прокси, события, минутная статистика, здоровье звеньев; с курсором для догрузки |
| `RunDiagnostics(scope)` | поток результатов проверок |
| `UploadArtifact(stream)` | заливка бинарника чанками; нода проверяет sha256/подпись |
| `StreamLogs(target, tail, follow)` | хвост логов контейнеров ноды |
| `UpdateSelf(version)` / `UpdateEdge(version)` | самообновление агента / передача edge |

**Произвольного выполнения команд нет.** Все изменяющие вызовы пишутся в журнал
ноды и в `audit_log` панели.

**Желаемое состояние ноды** (`NodeState`, целиком в каждом `ApplyState`):
поколение; настройки ноды (режим управления и `mgmt_sni`, пул доменов, чёрный
список, политика IP, цепочка по умолчанию); входы; прокси (с секретами — без них
нода не может работать); выходы и цепочки (с учётными данными); ссылки на
артефакты (движок, версия, архитектура, sha256); учётные данные DNS — только для
прокси этой ноды, которым нужен DNS-01. Нода валидирует
состояние целиком до применения и отклоняет его с причиной. На ноде
`data/state/*` доступны только root (0600); секреты не пишутся в логи и не
возвращаются в `GetInfo`/`Watch`.

**Edge ↔ агент** — gRPC по unix-сокету `data/run/edge-g<N>.sock`: `SetConfig`
(полная таблица + поколение), `Snapshot` (счётчики), `Events`, `Drain`, `Health`.
Edge сохраняет последнюю таблицу на диск и поднимается с ней без агента.

## 7. Обновления и версии

**Артефакты.** Ноды не обязаны ходить в интернет: панель скачивает релизы,
проверяет, кеширует (`/data/artifacts`) и заливает на ноды через `UploadArtifact`.
Режим «нода качает сама по ссылке из состояния» — опция (для нод, у которых
GitHub доступен, а панель далеко).

| Компонент | Источник | Проверка |
|---|---|---|
| telemt, mtg, xray, warp-plus | релизы GitHub апстрима (API с ETag) | sha256: из файлов сумм апстрима, если есть, иначе вычисляется **панелью** при первой загрузке и закрепляется в каталоге (TOFU) до заливки на ноды; нода только сверяет ожидаемый хеш и никогда не «доверяет вычисленному»; для канала stable — из нашего подписанного каталога. Берутся только статические/musl-сборки; после распаковки — пробный запуск `--version` в образе-раннере, иначе версия помечается непригодной |
| Postern (панель, нода) | наши релизы (Gitea сейчас, GitHub потом; для приватного Gitea — токен в настройках или ручная загрузка архива релиза в панель) | подпись minisign (Ed25519), публичный ключ вшит в бинарники |

**Каналы движков.** `latest` — всё, что вышло у апстрима. `stable` — версии,
прошедшие наш e2e в CI (плановая задача, §11): CI публикует подписанный
`engines-stable.json`. У прокси политика версии: «следовать каналу ноды/панели»
или «закрепить». В UI у каждого прокси видны «работает» и «должна быть».

**Раскатка.** Канарейка: один прокси → одна нода → все (вручную по шагам или
автоматически с паузой). Каждый шаг — blue-green с автоотменой; провал
останавливает раскатку и пишет событие.

**Самообновление (запускатель).** Бинарник лежит в томе; контейнер стартует
`launcher.sh` (POSIX sh) — он запускает `current`. Процесс после успешного старта
(30 с без ошибок) пишет маркер `healthy`. Если при запуске маркера прошлого
запуска нет — увеличивается счётчик сбоев; 3 сбоя подряд при наличии `previous` →
откат симлинка. Обновление: залить и проверить подпись → `current` на новую
версию, `previous` на старую → выйти с кодом перезапуска → Docker перезапускает
контейнер. Спутников и сборок нет.

- **Агент:** прокси не замечают (edge и движки — отдельные контейнеры).
  Маркер `healthy` агент пишет, когда поднят gRPC-сервер, состояние загружено и
  первый проход согласования завершился без фатальной ошибки — а не просто через
  30 с жизни процесса.
- **Edge** (порядок важен — ядро сразу распределяет новые SYN между всеми
  сокетами группы `SO_REUSEPORT`):
  1. агент пишет `edge/config-g<N+1>.json` **до** запуска;
  2. поколение N+1 стартует, читает таблицу и **только потом** занимает входы и
     SOCKS-порты (те же адреса, `SO_REUSEPORT`, тот же UID; userns-remap Docker не
     поддерживается — это проверяется при установке);
  3. N+1 сообщает готовность, агент ставит N `restart=no` и вызывает `Drain`
     (закрыть слушатели, дождаться 0 соединений или 1 ч), затем удаляет N.
  Если сервер перезагрузился посреди передачи и поднялись оба поколения, агент
  при старте сливает старшее (инвариант «одно активное поколение edge»).
  Агент суммирует **приращения** счётчиков по каждому поколению, поэтому смена
  поколения не обнуляет графики.
- **Панель:** образ из реестра + та же схема «бинарник в томе». Перед миграцией
  схемы БД — автоматический снимок БД в `/data/backups` (`VACUUM INTO`, а не
  сырая копия файла: при WAL копия файла может быть несогласованной).

## 8. Панель

### 8.1 Бэкенд

Go, SQLite (`modernc.org/sqlite`, без CGO, WAL), запросы — `database/sql` с
тонким слоем репозиториев, миграции — встроенные SQL-файлы. API для браузера — ConnectRPC (JSON по HTTP/1.1, тот же
protobuf, `proto/postern/panel/v1`), клиенты TS генерируются. SPA встроена
(`embed`). Фоновые задачи: менеджер соединений с нодами (поток `Watch`,
переподключение с backoff, отправка состояния при изменениях и при
`applied < desired`), загрузка статистики и свёртки, трекер релизов, кеш
артефактов, планировщик проб из панели, обновление GeoIP.

Каталог данных `/data`: `postern.db`, `master.key`, `artifacts/`, `bin/`,
`geoip/`, `backups/`.

### 8.2 Безопасность панели

- Первый запуск: одноразовая ссылка с токеном установки в логах → создание
  админа. Токен печатается один раз, действует 1 ч и только до создания первого
  админа. Пароли — argon2id; TOTP (по желанию, рекомендуется).
- `master.key` по умолчанию лежит **отдельно от БД** (`/keys/master.key`, отдельный
  том); бэкап каталога данных без ключа секретов не раскрывает.
- Сессии: случайный токен 256 бит, в БД — хеш; cookie `HttpOnly`, `SameSite=Strict`,
  `Secure` при TLS; срок 7 дней со скользящим продлением; выход отзывает сессию;
  смена пароля отзывает все сессии.
- CSRF: `SameSite=Strict` + запросы только `application/json`/Connect (простые
  кросс-доменные формы невозможны). Лимит попыток входа на IP и логин, блокировка
  с экспонентой.
- Секретный путь к админке (опционально), белый список IP админки (опционально),
  админка недоступна на домене публичной страницы.
- Секреты не отдаются в API без необходимости: токены Cloudflare, ключи — никогда;
  секрет прокси — только в ссылках и на странице прокси.
- TLS панели: собственный ACME (если задан домен и доступны 80/443) или внешний
  обратный прокси/Cloudflare; по умолчанию HTTP на выбранном порту (домашние
  установки за NAT).

### 8.3 Экраны

- **Обзор:** плитки нод (онлайн, версии, CPU/RAM, соединения, трафик за сегодня);
  лента проблем.
- **Нода:** сводка (ОС, публичные IP, владельцы портов); входы; прокси; цепочки и
  здоровье звеньев; версии и обновления; диагностика (отчёт + запуск); логи в
  реальном времени; пул доменов и чёрный список; мастера добавления (SSH / ручная
  команда).
- **Прокси:** список по всем нодам с фильтрами (нода, тип, статус, метки, движок,
  «устарел») и массовыми действиями (пауза, выход, движок/версия); страница прокси:
  ссылки (`tg://` и `https://t.me/...`), QR, живые соединения/устройства, графики,
  IP со странами, настройки (лимиты, выход, движок и версия, тонкие параметры),
  действия (пауза, смена движка, сброс соединений, проба, перевыпуск сертификата).
- **Выходы:** профили, подписки, цепочки, здоровье по нодам, проверка.
- **Версии:** каталог движков (latest/stable, changelog), раскатка, версии агентов,
  edge и панели.
- **Журнал:** действия и события.
- **Настройки:** админы и TOTP, доступ к админке, хранение статистики, политика IP,
  GeoIP, учётные данные DNS, публичная страница.

Интерфейс — русский и английский (i18n с первого дня), тёмная и светлая темы.
Стек: React + TypeScript + Vite, Mantine (+ charts), TanStack Query, i18next.

### 8.4 Статистика

Хранение и свёртки — §3. Графики: трафик, соединения, устройства по прокси и
нодам; топ прокси; IP со странами. Страна по IP — офлайн-база DB-IP Lite Country
(CC BY 4.0, атрибуция в «О программе»), обновляется панелью раз в месяц; браузер
во внешние сервисы не ходит.

### 8.5 Публичная страница

- Отдаётся панелью на **отдельном домене** (маршрутизация по `Host`; админка там
  недоступна). Удобно прятать за Cloudflare: реальный IP панели не светится.
- Открыта на корне домена (решение владельца); заголовок `X-Robots-Tag: noindex`
  и `robots.txt` по умолчанию (переключатель). Выключена, пока админ не задал
  домен и не включил её явно.
- Админ выбирает прокси и порядок, публичное имя и заметку, заголовок и текст
  (Markdown, без HTML).
- По каждому прокси: кнопка «Подключить» (`tg://`, запасная `https://t.me/...`),
  ручные параметры (сервер, порт, секрет; для WEB — сервер и секрет) с
  копированием, QR (SVG).
- Недоступные (пауза, нода офлайн, проба провалена) — скрыть или пометить.
- Рендер на сервере (html/template), без обязательного JS, RU/EN.

### 8.6 Политика IP

`full` — история IP с последним визитом и страной (7 дней по умолчанию);
`countries` — только агрегаты по странам, IP не хранятся; `off` — ничего. IP-данные
пользователей из стран с блокировками чувствительны, поэтому срок хранения
короткий и настраиваемый.

## 9. Разворачивание нод

**По SSH из панели** (основной путь). Вход: адрес, порт, пользователь, пароль или
ключ (не сохраняются, если не отмечено иное; при сохранении — `*_enc`).

1. Предпроверка: ОС и архитектура, Docker и его версия, свободное место, занятые порты
   и кто их держит (remnawave/Xray, nginx, caddy),
   публичные IP, часы.
2. Docker: если уже установлен — используется как есть. Иначе, с
   подтверждением в мастере, — официальный способ get.docker.com, а если он
   недоступен (бывает из РФ) — пакеты дистрибутива (`docker.io` +
   `docker-compose-v2`). Проверка, что userns-remap выключен (§7).
3. Заливка `launcher.sh`, бинарника ноды, `compose.yaml`, PKI; запуск агента.
4. Панель подключается по mTLS, проверяет `GetInfo`, нода переходит в `online`.

Ход установки транслируется в UI потоком. Повторный запуск идемпотентен.

**Ручная установка** (запасной путь): панель отдаёт пакет `postern-node-bundle.tar`
(CA + сертификат и ключ ноды + порт) **файлом** — его копируют на сервер (scp) и
запускают `install.sh --bundle <файл>`; скрипт делает шаги 2–3, бинарник берёт из
релиза по ссылке. Вариант «команда с пакетом в base64» отброшен (Ruling 39): ключ
ноды попадал бы в историю оболочки. Вместо него — пакет файлом (этот путь) и
установка по SSH из панели (основной путь, срез 4).

## 10. Безопасность (сводка)

| Угроза | Мера |
|---|---|
| Перехват управления | mTLS с собственным CA, закреплённый отпечаток ноды, без токенов в открытом виде |
| Обнаружение ноды сканером | режим `hidden` (управление за портом прокси по SNI), маска/отказ для чужих |

| Слишком широкие права агента | агенту нужен docker.sock (≈ root) — это принято и задокументировано; удалённого выполнения команд нет |

## 13. Тестирование

- **Unit:** ссылки — золотые векторы, совпадающие байт в байт с эталонными формулами §4
  (включая `encodeURIComponent`, регистр, IPv6); рендер конфигов — снапшоты на
  движок; цепочки — фейковые дайлеры; согласование — фейковый Docker; лимиты и
  счётчики edge.
- **Фаззинг** всего, что парсит данные из сети или от пользователя: ClientHello,
  PROXY-заголовок, URI выходов, подписки.
- **Интеграция:** настоящий Docker, настоящие бинарники движков.
- **e2e на стенде:** создать прокси, пауза, смена движка, обновление версии, отказ
  звена выхода, рестарт агента без разрывов, передача edge.
  Уровень L1 — без интернета; L2 — когда есть доступ к DC.
- **Безопасность:** govulncheck, gosec, проверка отсутствия секретов в логах.
- **Приёмка вручную** на тестовой VM с реальными клиентами по чек-листу в `docs/`.

## 14. Риски и что проверить на реальных серверах

1. ME через SOCKS: работает ли middle-proxy с `middle_proxy_nat_ip` = IP выхода;
   нужен ли ME вообще без промо-тега.
2. telemt: точный набор назначений апстримов (`me`, `fetch`, …) и что все они
   уходят в SOCKS edge; поведение `tls_fetch_scope`.
3. mtg v2: точные ключи конфига, PROXY protocol на слушателе, socks-апстрим,
   имена артефактов.
4. warp-plus: флаги, хранение регистрации, работоспособность WARP из РФ.
5. Xray: поддерживаемые транспорты и протоколы в выбранной версии (xhttp и т. п.).
6. `SO_REUSEPORT`-передача edge между контейнерами (тот же UID в host network).
7. WEB через edge: Telegram Desktop (HTTP/2, long poll, WebSocket), iOS (только `https`).
8. Лимит устройств за NAT (несколько устройств на одном IP).
9. Пороги расхождения часов для fake TLS.
10. Docker Desktop (локальная разработка): особенности host network — e2e
    гоняется целиком внутри одного Docker-хоста.

## 15. Журнал решений (кратко)

1. Прокси = ссылка; «клиент» отложен.
2. Панель → нода по mTLS; режим `hidden` для порта управления.
3. Docker как среда исполнения, но без своих образов на ноде: `alpine` + бинарники.
4. Свой edge вместо nginx: выборочный PROXY protocol, атомарная таблица без
   reload-граблей, счётчики и лимиты независимо от движка, WEB-терминация с
   реальным IP.
5. Один экземпляр движка на прокси в v1; абстракция допускает общий экземпляр.
6. Фоллбек выхода — в edge, по звеньям; протоколы — во внешних процессах
   (Xray, warp-plus).
7. Декларативное состояние с поколениями и согласованием.
8. Обновления через артефакты, подписи и blue-green; канал stable — результат
   нашего e2e, а не пересборка.
9. SQLite в панели и в буфере ноды; ConnectRPC для браузера и gRPC для нод на
   одном protobuf.
10. Публичная страница — открыта на корне отдельного домена, `noindex`.

## 16. Внешнее ревью (Grok, 2026-10-04) — что принято

Принято и внесено выше: PROXY v2 на скрытом слушателе управления перед mTLS
(§5.3); TLS-ALPN-01 → бэклог, в v1 DNS-01 (§5.4); переопределения цепочек по
назначению `me`/`fetch` (§5.6); порядок
передачи edge «таблица до привязки», одно активное поколение, стабильные
SOCKS-порты (§5.6, §7); `public_addr` из A-записи (§5.4); сниппет без слеша и
доверенные подсети для режима 3 (§5.4); гейт blue-green с проверкой выхода
(§5.5); сериализация согласования (§5.2); mtg — полный `ee`-секрет и запрет при
промо-теге (§5.5); только статические сборки и проверка запуском, хеш
закрепляет панель (§7); `master.key` отдельно от БД, пакет ноды файлом,
одноразовый токен установки (§8.2, §9); горячая подмена сертификатов в edge
(§5.4); запрет перекрывающихся входов (§3); carrier `https` по умолчанию ради
iOS (§5.4); падение звена только по DC (§5.6); приращения счётчиков и критерий
`healthy` агента (§7); страница выключена до явной настройки (§8.5); Docker из
пакетов дистрибутива, если get.docker.com недоступен (§9); подпись «уникальные IP»
(§3).

Отклонено/уточнено: утверждение, что старая ссылка оставляет `:` IPv6 без
экранирования, неверно — `encodeURIComponent` экранирует `:` как `%3A`;
поведение закрепляется золотыми тестами. Изоляция экземпляров отдельными UID и
nft — в бэклоге (§0.2).
